Numbers are the order things happen. Every scan ends with the Notary, even one that was refused or stopped early, so there is always a record you can check later.

Act 1 · Getting in

Before anything touches your site.
01

You make a request

In the console you paste the website address, pick how deep to go and confirm you're allowed to test it. Without that yes, nothing runs.

Or from the command-line client, Postman or your own app.

02

The front desk checks your pass

Your sign-in token is checked, then your role: viewers read reports, scanners run normal scans, admins run deep and signed-in scans. A page from another website can't use your pass.

03

You wait your turn

One scan runs at a time. Others join a line of up to 50 and see their place. When the line is full you're asked to try again later.

04

The Gatekeeper

validate

Draws the fence: your site, its www. twin and any domains you named. It refuses addresses no scan may ever reach, like a cloud's internal metadata service.

05

You decide what to test

choose_scopeasks you

Before anything touches your site, the scan asks: the website and its source code, the website only, or only the code? Code only skips the Explorer, and the helpers who would visit the site just pass it on, so you don't even need a website. Pick it right in the console's New scan card and give the code there (files, a .zip or a git link); then it doesn't wait. No answer in time: the default.

Act 2 · Looking around

Learning what the site is made of.
06

The Explorer

reconvisits your website

Walks through your pages and public signposts (robots.txt, sitemaps, security.txt). Links to other websites and links to files (installers, archives, documents) are written down but never followed.

07

The Login helper

authvisits your website

If you gave login details, signs in so the logged-in pages can be tested too. It notices when a login really goes to a single sign-on provider or asks for a second factor, and never pretends that worked.

08

You, when asked

auth_challengeasks you

Only if you ticked "pause for SSO / MFA": the scan waits and asks you. For a one-time code you type it in; for single sign-on you sign in in your own browser and hand over just the session. Your password and second factor never reach the agent. No answer in time: the scan continues as a visitor.

09

You, with your code

code_sourceasks you

If you chose to include code, at the code step the scan waits and asks you for your app's source code: pick some code files or a .zip, paste the .git link of a public repository (GitHub, GitLab, Bitbucket; any branch or tag), or skip. The link is checked first, so you can fix it if it can't be reached. Choose "website only" and it never asks. No answer in time: the website is tested on its own (with "code only", nothing is analysed).

10

The Code analyst

code_sastsealed box

Reads the code you gave (Python only for now) inside a sealed box with no internet: risky patterns, leaked secrets, missing access checks, unsafe settings. A git link is copied first (latest version only, no passwords). Nothing is ever run; files that aren't Python are marked as only partly checked, programs and batch files (.exe, .bat) are flagged as warnings and shell scripts noted, and every finding comes with how to fix it, in the same report.

11

The Code reader

sandbox_checksealed boxreads your pages

Copies the text of your website's pages and scripts into a sealed box with no internet and reads that code for risky patterns. It never runs anything; the box is destroyed when it's done, and its findings join the same report.

12

The Scanner

dastvisits your websiteisolated

Runs the main security tests from an isolated helper that may only make reading requests, only inside the fence, only to the addresses it checked at the start, and never downloads files.

13

The AI planner

plan_probesuses the AI

Looks at what's been found and picks extra checks from a fixed menu of safe ones. It chooses; it can't write code. Without an AI, a built-in plan is used.

Act 3 · Testing and writing it up

Careful, read-only checks, then the paperwork.
14

The Prober

run_probesvisits your website

Double-checks the plan, then runs those checks with reading requests only. A resumed scan doesn't ask the AI again.

15

The Collector

aggregate

Gathers every finding, removes duplicates, notes what couldn't be tested, and writes a factual summary where each statement points to its source, like [S1].

16

The AI writer

summarizeuses the AI

Drafts a friendlier executive summary, kept only if every claim cites a real finding; otherwise the Collector's summary stays.

17

The Publisher

report

Produces the report as a web page, a Word document, Markdown and JSON. Everything taken from your site is shown as plain text, so nothing in it can run in your browser.

18

The Notary

audit

Writes one record of the whole scan: who asked, what was scanned, how it ended, whether sign-in worked and a fingerprint of each report file. Records are chained and sealed, so any later edit shows. It never writes passwords, tokens or codes.

The rules every character follows

Stay inside the fence

Only your site and the domains you named. Outside links are listed, never visited; cloud metadata addresses are always off limits.

Read, don't change

Tests use reading requests. Nothing the AI suggests is ever run as code.

Nothing downloaded

Files on your site are never fetched; anything that isn't text is thrown away unread.

Sealed where it matters

Untrusted code is read inside boxes with no internet, destroyed afterwards. Saved progress is encrypted.

You stay in charge of sign-in

SSO and MFA are done by you; the agent only borrows the session for your site.

Everything on the record

Every scan, even a refused one, ends in a tamper-evident audit record you can verify later.
